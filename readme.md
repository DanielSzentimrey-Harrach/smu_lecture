# Spec-Driven Development Workflow

This project uses **Spec-Driven Development (SDD)**. The important idea is that the specification is
the source of truth for the work. Code implements the agreed requirements; it does not quietly create
new requirements of its own.

Use the following workflow when adding a feature to the calculator.

## 1. Create or review the constitution

Begin by creating the project constitution, or reading the existing one. The constitution defines the
project's permanent rules and boundaries. For this calculator, it establishes decisions such as:

- Java with Swing and Maven
- Java 25 as the target version
- BigDecimal for arithmetic
- a simple architecture with business logic separated from Swing UI code
- strict test-driven development (TDD)
- no persistence, networking, or unnecessary third-party dependencies

The constitution is above any individual feature request. If a new idea conflicts with it, discuss and
amend the constitution before proceeding.

## 2. Ask the agent to write the feature specification

Describe the feature you want and ask the coding agent to create a numbered folder under `specs/` with
three files:

- `spec.md` explains **what** users need and why, using user-facing requirements and acceptance criteria.
- `plan.md` explains **how** the feature will fit into the existing project architecture.
- `tasks.md` lists the ordered implementation steps, including the TDD red-green-refactor cycle.

For example, a request to support keyboard input produced `specs/002-keyboard-input/`. Its specification
can state that number keys, arithmetic operators, Enter, Backspace, and Escape should work, and that
Shift-generated characters such as `*` from `Shift + 8` must be recognized too.

At this stage, do not jump straight to code. A clear spec gives both you and the agent something
concrete to evaluate.

## 3. Review and iterate on the documents

The human developer must review the generated `spec.md`, `plan.md`, and `tasks.md`. Read them as a
design proposal, not as automatically approved truth. Check questions such as:

- Is the behavior specific enough to test?
- Does it fit the constitution and the calculator's intentionally simple scope?
- Are important edge cases covered, such as division by zero or malformed input?
- Does the plan use the existing classes instead of inventing unnecessary layers?
- Do the tasks describe a sensible order of work?

Ask the agent to revise the documents until they describe the behavior you actually want. For example,
keyboard support should explicitly say whether `=` evaluates a calculation and whether `+` generated by
the keyboard layout is an operator, rather than leaving those details implicit.

## 4. Kick off implementation with TDD

Once the documents are reviewed, ask the agent to follow `tasks.md` and begin implementation. For logic
that can be unit tested, use this cycle:

1. **Red:** write one focused test for a requirement and run it to confirm that it fails for the expected
	reason.
2. **Green:** write the smallest production change that makes the test pass.
3. **Refactor:** improve names or structure without changing behavior, then run the tests again.

For example, before changing keyboard mapping, add tests that expect `Shift + 8` to resolve to `*` and
`Shift + =` to resolve to `+`. Confirm that the new tests fail against the current code, then update the
keyboard mapping and run the suite again. Swing wiring may be thin and difficult to unit test, but it
must delegate to the tested calculator behavior rather than duplicating it.

## 5. Iterate until the feature works

Continue through the tasks, running focused tests after each small change. Then run the complete Maven
test suite and, when appropriate, package and manually smoke-test the application. For this project,
use commands such as:

```text
mvn test
mvn verify
```

Test both the normal path and the important failure paths. A calculator feature is not complete merely
because `12 + 58` works; it should also preserve history correctly, handle decimals and negative values,
and show a controlled error instead of crashing on division by zero.

## 6. Retrofit new discoveries into the SDD files

During implementation, you may discover a requirement that was missing or unclear. Do not leave that
decision only in the code or in a conversation. Stop and update the relevant `spec.md`, `plan.md`, and
`tasks.md` files first, then continue implementing.

For example, if testing reveals that a keyboard event supplies `*` as the character while its key code
looks like the `8` key, update the keyboard spec and plan to document this case. Add or check off the
corresponding task, add the regression test, and then keep the implementation consistent with the
updated documents.

This final synchronization step keeps the repository teachable: a new student can read the constitution
and feature files, understand why the code behaves as it does, and reproduce the same workflow for the
next feature.
