Slide 5

What is spec-driven development?

Spec-driven development treats the specification as the source of truth. Code is a derived, regenerable artifact from that spec, not the thing that defines the project.

The SDD loop
Rules & Memory
Prompt
Spec
Check
Plan
Check
Implement
  • Specs are reviewed and versioned like code
  • AI implements against a spec, not instead of one
  • Every line of code maps back to a requirement
Slide 6

A full enterprise SDD workflow

Planning

Create the spec, examine the issue tracker, and stop for human review before implementation begins.

Implementation

Test first, implement second, then review the code and run checks before delivery.

Delivery

Reconcile the final branch against the spec, update constitution memory if needed, and complete the merge/PR cycle.

Slide 7

SDD addresses quality, security, and maintainability.

Quality

  • Specs and task breakdown happen before code is trusted
  • Review gates catch missing requirements early
  • Failures are visible before the branch is merged

Security

  • Governance and scanning are built into the pipeline
  • Security checks are not a last-minute add-on
  • Risk is managed continuously, not guessed later

Maintainability

  • The spec and plan persist as living documentation
  • The project memory keeps decisions consistent
  • Future changes have a record of why things exist

Slide 10

A hard problem the industry can't skip.

Vulnerability remediation is genuinely difficult at enterprise scale — and skipping it has never been the safe option.

The challenge
Huge codebases

Years of code across many repos and teams — more than any one person can hold in their head.

Extra work, not extra time

Remediation competes with feature deadlines instead of being part of them.

Volume outpaces capacity

Far more findings surface than engineers have time to review.

The real boundary is often invisible

Auth, encryption, and network policy frequently live one layer below the repository a scanner can see — a gap this deck comes back to directly.

Why it still matters
Risk doesn't wait

An unpatched vulnerability is exploitable regardless of available bandwidth.

A breach costs more than a fix

In damage, in trust, and in cleanup effort.

It compounds

New findings arrive continuously — the backlog only grows if the process doesn't scale.

Attackers automate too

Manual triage alone brings human pace to a fight the other side is already running at machine speed.

Slide 11

The end-to-end remediation workflow.

Complementary automated passes surface and cross-check findings against each other; a human stays the checkpoint at every decision that matters.

Scan & analysis

Independent scanning passes cross-check each other, get deduplicated and scored, then anything ambiguous is flagged for a human call.

Fix

Findings are triaged by severity, a remediation is chosen deliberately, implemented narrowly, and covered by a test — then reviewed before it moves on.

Verify & close

The fix is tested, built, deployed, and re-scanned — but only a human verifying it in the target environment actually closes a finding.

Slide 12

AI can be confidently wrong. That's why a human signs off.

Case 1 — a real false positive from the review gates in this deck.

Case 1 — False positive
  • Flagged: "Missing authorization check on password-unmask operation" — inside a service that subscribes to an encrypted Kafka topic, decrypts a password field, and writes it downstream.
  • Reality: only specific pre-approved service identities can publish or subscribe to that topic at all — enforced by the broker's access-control list, not by a check in this repository.
  • Why the model missed it: it only had this one codebase in view. The real authorization boundary lives one layer down, in infrastructure this repo never touches — "the whole project" was in context, "the whole system" was not.

Takeaway

Before accepting "missing check," ask where else in the stack that boundary might already be enforced — a network policy, a broker ACL, an API gateway, a service mesh. A scanner that only reads one repository can't answer that question. A human who knows the system's topology can — and a "fix" applied blindly here wouldn't have closed a real gap, it would have bolted a redundant, misleading check onto code that was never the actual boundary.

Slide 13

AI can be confidently wrong. That's why a human signs off.

Case 2 — a real wrong fix from the review gates in this deck.

Case 2 — Wrong fix
  • Flagged: an internal admin REST API for a Kafka-Connect-style pipeline worker had no authentication in front of it at all — a textbook "Missing Authentication for a Critical Function" (CWE-306).
  • AI's first fix: bolt on username + password — a shared secret that now has to be issued, stored, and rotated for every caller.
  • Root cause — same as Case 1: the model saw "no authentication" and reached for the generic textbook answer. It had no visibility into this team's actual convention: the rest of their Kafka estate already authenticates callers via mutual TLS through the firm's existing certificate infrastructure — that standard lives in platform config outside the one repo it was scanning.
AI's fix: username + passwordshared secret — issued, stored, rotated per caller
vs
Correct fix: mTLSclient certificate presented via the existing PKI
Two different mechanisms: a password is a shared secret sent with the request; an mTLS certificate proves identity during the TLS handshake itself — no secret travels over the wire.
Takeaway

When AI proposes a fix, check whether it matches how the rest of the system already solves the same problem. A textbook-correct answer that ignores local convention doesn't just add a few extra lines — a parallel credential scheme is a whole new secret to issue, store, rotate, and eventually forget about, sitting next to the certificate infrastructure the team already trusts.

Slide 14

The boring vulnerability-fix grind pays hidden XP.

Point AI at enough findings and it stops being just outsourced labor — it starts handing you a security education on the side.

Hidden XP #1 — CWE (Common Weakness Enumeration)
No more "it's some kind of injection thing"

The AI names the exact CWE ID behind the finding — e.g. CWE-89 — instead of a vague vibe.

Every number has a canonical definition

Look it up at cwe.mitre.org for a precise, searchable writeup — so "what is this, actually?" has a real answer.

Nobody knows every vulnerability class — yet

Not even the pros memorize the whole catalog. Every finding you triage quietly adds one more entry to yours.

Hidden XP #2 — CVSS (Common Vulnerability Scoring System)
A number, not a vibe

CVSS scores exploitability and impact on a 0.0–10.0 scale, so "this feels bad" turns into something you can actually compare.

The vector spells out the "why"

It breaks the score into how easy the bug is to trigger, what access it needs, and what it compromises.

The Critical / High / Medium bands

Critical (9.0–10.0): trivial to exploit, full compromise. High (7.0–8.9): serious impact, but usually needs a precondition. Medium (4.0–6.9): limited impact, or high impact with mitigating factors.
